Original goal
Make entire session resume <branch> read committed checkpoint metadata and transcripts from the v1.1 local custom ref when strategy_options.checkpoints_version is 1.1, while preserving existing v1 behavior otherwise. Hidden alias entire resume is covered by the same command path.

Hard constraints and decisions
- No fallback from v1.1 to v1. If v1.1 mode is enabled and refs/entire/checkpoints/v1.1 has no checkpoint metadata/transcript, resume should fail/report unavailable rather than read v1.
- v1.1 is local-only. Remote fetch/checkpoint_remote fallback remains a v1 behavior only.
- Do not add side effects to NewCommittedReadStore. It should choose the committed read ref, not seed/sync/write refs.
- Resume is read-only for committed checkpoints. It should not write to the v1.1 custom ref.
- Prefer the existing checkpoint committed store API over hand-rolled tree/ref reads.
- strategy.GetMetadataBranchTree is v1-only. It was not updated because the intended normal path is the checkpoint store API. If a future need requires strategy metadata parsing with arbitrary refs, add a shared ref-aware helper instead of resume-local tree code.
- Switching away from strategy.ReadCheckpointMetadata was necessary for v1.1 ref correctness only because the existing resume usage obtained its tree via strategy.GetMetadataBranchTree, which is hard-coded to entire/checkpoints/v1. The parser itself is not inherently wrong.

Implemented branch behavior
- resumeFromCurrentBranch constructs checkpoint.NewCommittedReadStore(ctx, repo), sets FetchBlobsByHash, and uses that store for committed checkpoint metadata reads.
- Multi-checkpoint squash resolution uses resolveLatestCheckpoint(ctx, store, checkpointIDs), so timestamps are resolved from the selected committed read ref.
- readCheckpointInfoFromStore reads checkpoint.ReadCommittedCheckpoint(ctx, store, checkpointID), then reads per-session metadata via store.ReadSessionMetadata. This keeps summary/session metadata on the same committed ref.
- readCheckpointInfoFromRef creates checkpoint.NewGitStoreWithRef(repo, committedReadRef), so remote/fetch retry paths continue with the same selected ref rather than implicitly defaulting to v1.
- checkRemoteMetadata accepts committedReadRef. If the ref is not the v1 branch, it prints that metadata is unavailable in that ref and returns. This enforces no v1 fallback in v1.1 mode.
- resumeSingleSession uses checkpoint.NewCommittedReadStore(ctx, repo) and checkpoint.ReadRawSessionLogForCheckpoint to restore transcript content from the selected committed read ref.
- ManualCommitStrategy.RestoreLogsOnly uses checkpoint.NewCommittedReadStore(ctx, repo) and ReadCommittedCheckpoint so resumeSession transcript restoration also follows the selected committed read ref.

Why the fallback should be removed
A review finding raised concern that moving resume to ReadCommittedCheckpoint might stop supporting old direct CheckpointInfo metadata at checkpoint root metadata.json. I added a local fallback to re-read the configured ref tree and call strategy.ReadCheckpointMetadataFromSubtree. That was too much local complexity and duplicated store behavior.

We audited the actual checkpoint population in this repo with GIT_NO_LAZY_FETCH=1:
- refs/heads/entire/checkpoints/v1: 3995 root metadata files, 3919 readable, 3919 CheckpointSummary, 0 legacy direct CheckpointInfo, 76 missing promisor blobs.
- refs/remotes/origin/entire/checkpoints/v1: 1538 root metadata files, 1538 CheckpointSummary, 0 legacy direct CheckpointInfo, 0 missing blobs.
- refs/entire/checkpoints/v1.1 is not present locally.
Conclusion: legacy direct metadata fallback is not justified for this branch. If legacy direct metadata compatibility matters generally, it belongs in the shared checkpoint read layer, not in resume-specific fallback code.
