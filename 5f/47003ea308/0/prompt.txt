what do you think of this review on 840 What the PR does
Adds four content-based "linkage signals" to checkpoint metadata (tree_hash, patch_id, files_changed_hash, session_files_hash) so the web can re-link checkpoints to commits even after the Entire-Checkpoint trailer gets stripped by a rebase/amend/filter-branch. It's purely additive — doesn't change current behavior, just adds fallback data.
The core tension in the Slack thread
Soph's main concern: the PR implies a safety net that isn't actually reliable. The signals have limits —

Tree hash changes on rebase if there are any conflicts or context changes
Patch ID is the most robust but only covers clean rebases
The other two derived signals need to be computed for every commit in the repo at lookup time, which is a real perf/architecture concern
Overall it risks communicating false confidence to users ("don't worry, linkage will survive") when there are still plenty of cases it won't

ashtom's take: collecting the data doesn't hurt, it just needs to wait on Darwin (the server-side cnent) to actually use it effectively. The PR description's claim that "the web can automatically re-link" was the bigger issue — the language oversells what's possible right now.
Paulo floated a different angle: moving checkpoint IDs to git commit headers (not trailers) since headers are harder to accidentally strip during normal message editing. The catch is you can't do it with standard git commit, only with plumbing commands, and it would invalidate signatures on rewrite.
Where things landed / next steps

PR is still open (draft → ready → currently open) — the scope expanded from just tree hash to all four signals, and the description language has been toned down
Web side work is blocked on Darwin — the fallback chain (patch_id → files_changed_hash → session_files_hash) needs server-side compute that doesn't exist yet; right now the web can only use tree hash
Paulo's ExtraHeaders idea is a separate potential PR worth exploring — simpler change, though it only helps entire commit not git cGit hooks / CLI guard rails were mentioned as a nice-to-have (detect stripped trailers post-rebase, prompt user to re-add), but that's a separate effort
Wording in the PR description needs updating to not oversell the web's current re-linking capability and can you use /review for this pr too please
