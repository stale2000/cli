cmd.Env is built via append(os.Environ(), "ENTIRE_TEST_TTY=0", "GIT_TERMINAL_PROMPT=0"). If ENTIRE_TEST_TTY is already present in the inherited environment (e.g. set to "1" by a CI wrapper), the pre-existing first occurrence wins and the appended "0" is silently ignored. This could cause the subprocess to believe it has a TTY and hang waiting for interactive input. The upsertEnv pattern or filtering before appending avoids this shadowing. Violates the rule requiring upsertEnv for ENTIRE_* env vars appended to os.Environ().

If the alternates file exceeds the 4096-byte read cap but no relative entry appears within the bytes that were read, rewriteRelativeAlternates returns ok=false and the caller falls back to serving the original, uncapped file. That means a relative alternate after a large comment/absolute prelude is still handed to go-git unrepaired, so the bug this wrapper fixes can remain. Consider having readAlternatesLines report truncation separately so the caller can avoid falling back to the original when data was intentionally capped.

IsolateGitConfigEnv does not clear GIT_CONFIG_PARAMETERS or other parent GIT_CONFIG_* variables beyond KEY_/VALUE_, so in-process tests can still inherit configuration injected by a parent Git process. This undercuts the intended isolation for production code paths that shell out with os.Environ(). Please clear or neutralize all GIT_CONFIG_* variables here as well, restoring them in cleanup if needed.

This helper still allows GIT_CONFIG_PARAMETERS (and any other GIT_CONFIG_* key not explicitly listed) through, even though those variables can inject git -c configuration into child git commands. That means GitIsolatedEnv does not fully isolate tests from parent Git config as the updated comment states. Consider filtering on the GIT_CONFIG_ prefix instead of enumerating only a subset before appending the known isolated overrides.
