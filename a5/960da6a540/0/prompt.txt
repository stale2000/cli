1. [high] Multi-context login still collapses same-core accounts into one entry
     - RecordLoginContext always derives the context name from contextNameForCoreURL(coreURL) (cmd/entire/cli/auth/contexts.go:67,151), and Upsert replaces any existing context with
       the same name (internal/entireclient/contexts/contexts.go:170).
     - That means logging into the same core as a second user overwrites the first context instead of creating another one. So the new “multi-context auth” flow still can’t actually
       store multiple identities for one issuer.
 2. [high] entire auth revoke does not honor context-backed logins
     - newAuthRevokeCmd wires runAuthRevoke to auth.NewStore() instead of auth.NewContextStore() (cmd/entire/cli/auth.go:477-500).
     - As a result, users who are “logged in” only via contexts.json (for example, after switching contexts or after a login created by another CLI) get not logged in from entire
       auth revoke --current. Even worse, when revoking by ID, the cleanup path only deletes the legacy keyring entry, leaving the active context token in place
       (cmd/entire/cli/auth.go:517+).
 3. [medium] Running the git helper can unexpectedly switch the user’s active CLI context
     - git-remote-entire calls auth.MigrateLegacyLoginContext() on startup (cmd/git-remote-entire/main.go:81).
     - If migration is needed, it calls RecordLoginContext, which unconditionally sets f.CurrentContext = name (cmd/entire/cli/auth/contexts.go:69-79).
     - So a first git clone entire://... after upgrade can silently change current_context, altering which account later control-plane commands run under. Migration should preserve
       the existing current context when one is already set.

1. [high] New-cluster resolution can pick the wrong account when multiple contexts share one core
     - ResolveContextForCluster takes matches := f.ContextsForIssuer(coreURL) and then blindly uses matches[0] in internal/entireclient/clusterdiscovery/resolve.go.
     - After this branch, same-core multi-user contexts are supported (alice@core, bob@core), but first clone against a new cluster will auto-bind whichever one was saved first, not
       the active context.
     - Result: git clone entire://... can silently authenticate as the wrong user.
 2. [medium] Legacy-login migration skips same-core/different-user identities
     - MigrateLegacyLoginContext bails out when len(f.ContextsForIssuer(claims.Issuer)) > 0 in cmd/entire/cli/auth/contexts.go.
     - That only checks issuer, not (issuer, handle).
     - If contexts.json already has alice@core from another CLI, but the legacy entire keyring token is bob@core, migration is skipped and Bob never gets a context.
 3. [medium] User-facing auth errors point at the wrong CLI/command
     - internal/entireclient/clusterdiscovery/discovery.go tells users to run entire-core auth login --base-url <url>.
     - internal/remotehelper/transport/inforefs.go says please run 'entire-core auth login'.
     - This repo ships entire, not entire-core, and login here is not a --base-url command. So the recovery instructions are misleading.
 4. [medium] Replica cache updates are still racy across processes
     - internal/remotehelper/replicas/Persist and Invalidate do LoadCache → mutate → SaveCache.
     - SaveCache locks only the write; the whole read-modify-write sequence is not atomic.
     - Two concurrent clone/fetch/push processes can overwrite each other’s nodes.json updates and lose cache entries. This is the same class of race contexts.Modify(...) was added
       to avoid.
